## Cleanup plan: remove Lovable Cloud remnants

Now that your database, auth, and hosting all live outside Lovable, the repo can be simplified so nothing still reaches for the old Cloud project or its managed files.

### 1. Collapse env fallbacks to a single source of truth
- `.env` is currently rewritten by the Cloud integration. Replace its contents with the external Supabase values (same as `.env.local`) so both files agree, and remove `.env.local` (or keep just one — your choice).
- In `src/integrations/supabase/auth-middleware.ts`, drop the `SB_*` fallbacks and read only `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` (or the plain `SUPABASE_*` names your host injects). Same for `client.server.ts` — pick one naming scheme (`SUPABASE_*` or `SB_*`) and use it everywhere.
- In `src/routes/api.public.scan.ts`, replace the `SB_PUBLISHABLE_KEY`-based auth check with a dedicated `SCAN_CRON_SECRET` header check (better hygiene — the cron secret shouldn't be the same value as your publishable key).

### 2. Remove auto-generated Cloud integration files that no longer apply
The files under `src/integrations/supabase/` (`client.ts`, `client.server.ts`, `auth-middleware.ts`, `auth-attacher.ts`, `types.ts`) were auto-generated by the Lovable Cloud integration. Since you're now managing Supabase yourself in GitHub:
- Keep them as regular source files (they work fine), OR
- Move them to a non-`integrations/` path (e.g. `src/lib/supabase/`) so future Lovable edits don't try to regenerate them. Update all imports accordingly.

Recommendation: keep them in place for now — moving them is a large mechanical rename and provides no runtime benefit once you stop editing in Lovable.

### 3. Regenerate `src/integrations/supabase/types.ts` from the new project
The current `types.ts` was generated from the old Cloud database schema. Once removed on your own machine via `supabase gen types typescript --project-id tidjygzrpsqyaznrlrhe > src/integrations/supabase/types.ts`, commit it. (This is a local step for you — not something to do inside Lovable.)

### 4. Delete stale references
- `.lovable/plan.md` — leftover planning note about the fallback pattern; safe to delete.
- `supabase/config.toml` — auto-generated for the old Cloud project ref. Either delete it or overwrite with your new project ref if you plan to use the Supabase CLI locally.

### 5. Verify nothing else calls Cloud
Grep for `nvuipjvufgyorrgyarkj` (old project ref) across the repo and remove any stray references.

### What I will NOT touch
- `src/lib/push/config.ts` (VAPID public key — already correct)
- Business logic in `src/lib/jobs/*`, `src/routes/**`, `src/components/**`
- Your `.env.local` values
